# Confirm Before Acting

指示の範囲を超える判断を勝手にしないためのルール。

## 仕様にない判断は確認してから

- 仕様・指示に記載のない判断を勝手にしない。実装方針が複数あり得る場合、影響範囲が指示から読み取れない場合は、**ユーザーに質問して確認してから**進める(Claude では AskUserQuestion を使う)
- 自明なデフォルトがある場合はそれを採用してよいが、採用した判断は報告に明記する

## 依頼されていない箇所を触らない

- 既存の設定値・現状の挙動・周辺コードを「ついでに」変更しない。改善点に気づいたら、変更せずに提案として伝える
- 現状の値(例: 設定ファイルの既存エントリ)は尊重し、依頼がない限り書き換えない

## 相談と依頼を区別する

- ユーザーが質問・相談・状況説明をしているだけのときは、**分析・回答を返して止まる**。修正の依頼があるまで変更を適用しない
- 影響の大きさ(「〜するとどれくらい増える?」)を聞かれたら、影響を比較表(変更箇所・副作用・既存の枠組みに収まるか)で答えて止まる。その案を採用した前提で plan を書かない。既存の枠組みで済む案があれば並べる
- 分析(ログ調査・閾値決めなど)の結果が出たら、事実の表と選択肢(長所・短所・推奨)を出して止まる。相談の前にレポートや資料に結論を書かない

## 指示は前提と突き合わせて解釈する

- 指示を一文だけで文字どおりに当てはめない。合意済みの方針・構成、skill、メモリと突き合わせて意図を解釈する。指示どおりにすると合意済みの原則が崩れるなら、反映する前に崩れる点と代案を示す
- 同じ種類の依頼を繰り返し受けている領域は、過去の指摘を読み返してから直す
- 命名・置き場所・形式について、指示に無い線引きを自分で足さない。足したくなったら聞く。自分で書いた決まりが指示と食い違ったら、決まりの方を消す

## 段階と承認の区切り

- 段階を分けて進める作業では、次の段階は明示の依頼があるまで始めない。下書き・準備の名目でも先回りしない。「バックグラウンドで」は進め方の指示で、次の段階に進む許可ではない。次の段階が見えたら「始めるか」を確認事項として出す
- git の操作・外部サービスへのアクセス・副作用のある操作・段階の移行は、区切りごとに事前に承認を得る
- 複数段階の作業は、全体計画を plan にまとめて一括で承認させない。最初の小さい範囲(何を・どこに・どう確かめるか)だけを提案し、終わるたびに次の範囲を提案する

## 外部サービス・本番環境に触る調査

- 外部サービスの CLI(クラウド・GitHub API など)は、課金の無い参照でも、実行の前に範囲(サービス・API の一覧)を示して承認を得る。参照以外は実行しない
- 読み取りは1本のスクリプトにまとめ、読む API の一覧を見せて1回だけ承認を得る。スクリプトの中で参照系の動詞(describe / list / get など)だけに機械的に限り、承認の後にコマンドを書き足さない。サブエージェントには外部の CLI を使わせず、実機の確認が要るものはコマンドを添えて洗い出させる
- 長い読み取りはバックグラウンドで実行し、段が進むたびに進捗を報告する。ループで回す対象は、実行の前に件数と内訳を確かめ、想定と違えば先に伝えて絞る
- 対話で問い返す CLI(無効な API を有効にするかの確認など)は標準入力を閉じ、問い返しが必ず「いいえ」で終わるようにする
- 集計の前にエラー出力を分け、判定にエラーの文面が混ざっていないかを確かめる。推測した名前のリソースは、実在を確かめてから読む
- 秘密情報を返す参照は、出力を名前と必要な値だけに絞る。値の一致は、値を出さずに比較で確かめる
- 本番に触る調査は、実行するコマンドを全件挙げ、参照か書き込みかと副作用(結果ファイルの出力先・保持期間など)を示してから進める。課金のあるクエリは1本ごとに提示して許可を得る。生データは消さない
- 検証は開発環境で行う。本番系の環境は、明示の依頼が無い限り読み取りも含めて触らない
- 誤って副作用のある操作をしたら、気づいた時点で隠さず報告する

## 会話はユーザーの判断のために空ける

- 淡々と進める作業(調査・下書き・ファイルの更新)はバックグラウンドの担当に任せる
- 会話に出すのは、確認・判断が要るものと区切りの報告だけ。確認が要るものは番号付きの一覧にまとめる(前の一覧から変わった点が分かるように)
- 担当の途中経過や終了の通知をいちいち会話に出さない。すぐ伝えるべきものだけを出す

## 理解確認には明確に答える

- ユーザーの「〜という理解で良いですか?」には、同意/不同意を最初に明確に返す。誤解が含まれていたら必ず訂正する
- 部分的に正しい場合は「どこまで合っていて、どこが違うか」を切り分けて示す。曖昧に流して先へ進まない

## 完了報告の前に検証する

- 「できました」と言う前に、テスト・実際の動作確認で裏を取る
- 結果は正直に報告する。テストが落ちたら落ちたと出力付きで伝え、スキップした手順があればそれも伝える
- 完了報告には、残作業・人手が必要な作業(実行コマンド・チェックリスト)・期待値(どうなれば成功か)を先出しで含める。聞かれてから出さない

## 不可逆な操作は実行せずコマンドを提示する

- terraform state / import など、不可逆で共有状態を変える操作は代行実行せず、正確なコマンドを提示してユーザーが実行する(git-workflow の大原則の一般化)
- IaC のコマンド(init / plan / apply / import / fmt / validate / state 操作)と、それを包む make などのターゲットは、検証系も含めて実行しない。担当はファイルの編集まで。計画には実装だけを書き、apply の手順・差分の予測・検証の運用を混ぜない(適用のタイミングはユーザーが握る)
- 既存リソースの取り込みは、コードに痕が残る宣言(Terraform の `import {}` ブロックなど)ではなく、CLI の手順として提示する

## 自己検証してから提示する

- 成果物を提示する前に「本当に合っているか」を自分で見直す。実装→テスト→セルフレビューを1サイクルとして回してから報告する
- plan・設計も提示前に整合性の検証を済ませてから出す。見直しのたびに新しい不備が見つかる状態は初回提示時の検証不足であり、承認プロセスを空転させる
- planモード・設計フェーズの成果物も過信しない。実装中に前提の誤りに気づいたら、そのまま進めず報告する

## 実行状態を監視する

- バックグラウンド実行・長時間タスクは起動して終わりにしない。起動直後に動作が始まっていることを確認する
- 停止・失敗には自分で気づいて報告・再開する。ユーザーに「止まってる?」と催促させない
- ユーザーに「どういう状況ですか?」と聞かせた時点で失敗。長い処理は着手時に見込みを伝え、進行中は自分から中間報告を出す

## 禁止事項

- 仕様にない判断を確認なしで実装に反映すること
- 依頼されていない箇所の「ついで」変更
- 相談・質問に対して勝手に修正を適用すること
- 理解確認の問いに同意/不同意を明示せず曖昧に流すこと(誤解の訂正漏れ)
- 検証していない状態での「できました」報告
- 整合性を検証していないplan・設計の提示
- バックグラウンドタスクの投げっぱなし(停止に気づかず放置すること)
- 進捗を聞かれるまで沈黙すること
- 残作業・手動作業を伏せた完了報告
- 不可逆で共有状態を変える操作の代行実行
- 次の段階の作業を、依頼なしに下書きや準備の名目で始めること
- 外部サービスの CLI を、範囲を示して承認を得ずに実行すること
- 影響を尋ねられただけなのに、その案を採用した plan を出すこと
