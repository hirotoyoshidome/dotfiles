# Document Writing

初稿で通る資料にする。読み手を決めずに書き始めない。直すときは差分で直す。

## 依存する skill

- 同じディレクトリの `words.tsv`: 「完成文書の条件」のうち、判定が「語」の項目の辞書

## 書く前に読み手を確定する

- 読み手(上司・営業・他チーム・チーム内・将来の保守者)、用途(判断を仰ぐ・報告・手順として実行・記録)、貼り先、トーンを確認する
- 分からなければ書き始める前に聞く。調査範囲・深さの質問と同時に聞く
- 読み手は会話を知らない前提で書く

## 骨子で合意してから本文を書く

- 本文の前に「冒頭の結論1行・見出し構成・各情報の置き場所」を示して合意を取る
- 「口語で」等の書きぶりの指示は、短いサンプルで確認してから全体に適用する
- チャットでの脇道の質問を資料に入れるかは都度確認する

## 完成文書の条件

他者が読む文書が、提出時点で満たすべき条件の正本。書くときはこの節を満たす。他の skill には同じ条件を書かず、この節を参照させる。

- 判定: **語** は `words.tsv` の辞書で機械的に検出する。**読解** は文書を読んで判定する
- 完成文書から判定できない条件(読み手の確認・骨子の合意・置き場所・コマンドの実行確認など)はここに置かず、各 skill に置く

### 構成

| ID | 判定 | 条件 |
|---|---|---|
| S1 | 読解 | 結論が冒頭で読み取れる |
| S2 | 読解 | 文書の種類ごとの型に沿う。報告: 結論(対応可能か) → 追加で必要なもの → 詳細。レビュー: 判定(マージ可など)を1行目に → 「懸念 / 該当箇所 / 確認結果 / 対応不要ならその理由」の表。手順書: 重大な前提(止めてから実施する等)を強調 → 手順。残作業: 残っている作業だけ(完了したものは消す)。技術レビュー資料: 非機能(コスト・性能・同時実行・ログ・監視)の章と、未着手タスクの先出し |
| S3 | 読解 | 本文には読み手の判断・行動を変えるものだけを置く。対象外・不採用(理由を1行ずつ)、問題なしだった詳細や実測値(「参考」として)は末尾の1節にまとめ、本文と同格の節を立てない |
| S4 | 語・読解 | 確かめ切っていない「要確認」や、ユーザーが判断できる論点を残さない(確かめてから書く・質問して片付ける) |
| S5 | 読解 | 比較・条件分岐・課題・リスクの列挙は、散文ではなくまず表・マトリクスで一望できる形にする。詳細説明は表の後に置く |
| S6 | 読解 | リスクは「何が起きたら困るか+それをどう検知するか+発生確率の見立て」の定型で書く |

### 会話・作業の痕跡

| ID | 判定 | 条件 |
|---|---|---|
| T1 | 読解 | AIとの会話の経緯(「当初〜と報告したが誤り」)や作業ログを書かない |
| T2 | 語 | セッションの用語(「引継ぎ」「進捗」「ご相談したいこと」)を書かない |
| T3 | 語・読解 | 作業した主体(「AIが確認済み」)や決めた人の帰属を書かない。決定内容と正本の所在だけを書く |
| T4 | 読解 | 資料自体の位置づけ(commit対象か一時資料か)を本文に書かない |
| T5 | 読解 | 状況が変われば嘘になるステータスを書かない。満たすべき状態を書く |
| T6 | 読解 | 調査の経緯・その場の逸話・特定インシデント由来の記述を焼き込まない。読者にとっての客観的な要件・事実だけを書く |

### 言葉選び

| ID | 判定 | 条件 |
|---|---|---|
| L1 | 読解 | 観点・見出しはユーザー自身の言葉(質問文)をそのまま使う。造語・内部の呼び名・抽象的な名詞句を使わない |
| L2 | 読解 | 増減する件数を書かない |
| L3 | 語 | 「ほぼ」「実質」等の曖昧語を使わず、断定するか「未計測」と明示する |
| L4 | 語 | 「おまけ」「とりあえず」「一応」など、成果物を矮小化する・自信のない語を書かない。本当に不要なものなら消し、必要なものなら正当な理由を書く |
| L5 | 読解 | 共有ドキュメントでは、否定的・マイナスに読める表現を避ける(読者は書き手の事情を知らない) |
| L6 | 語・読解 | 特定の読者層を持ち上げる/見下すような区分表現(「人間向け」等)を使わない |
| L7 | 読解 | 注意書きは今回の対象に当てはまる事実だけ。対象外の条件の最悪ケースを断定で一般化しない |
| L8 | 読解 | 推奨には前提にしたパラメータと、根拠の種類(今の差か、将来の余裕か)を添える |
| L9 | 読解 | 異なる軸(ビジネス上の優先度と対応コスト等)を同じ並びで扱わない |
| L10 | 読解 | レビュー・指摘の資料では該当箇所と事実を示す。粗探しや頼まれていない観点は入れない |

### 他者の領域

| ID | 判定 | 条件 |
|---|---|---|
| O1 | 読解 | 相手が決めること(修正方針など)を提案しない。担当外の資料(他部署向けの早見表など)を作らない |
| O2 | 読解 | 他システムの不足を名指しせず、自分側の対処として書く |

## 修正は差分で行う

- 指摘された箇所だけを直す。全文を書き直さない
- 「冗長」と言われたら量を減らす。直した後に行数が増えていないか確かめる
- 修正の報告は変えた点を数行で伝える

## 既存 skill との線引き

- 分量と取捨選択の基準は concise-writing、置き場所は deliverable-presentation、判断ログは preserve-reasoning、手順のコマンドは reproducible-runbook
- この skill は、読み手の確定から差分修正までの手順と、完成文書の条件を扱う

## 禁止事項

- 読み手・用途・貼り先を確かめずに書き始めること
- 骨子の合意なしに長い本文を書くこと
- 「完成文書の条件」に反したまま提出すること
- 修正のたびに全文を書き直すこと、「冗長」の指摘に量を増やして応えること
