# Document Writing

初稿で通る資料にする。読み手を決めずに書き始めない。直すときは差分で直す。

## 書く前に読み手を確定する

- 読み手(上司・営業・他チーム・チーム内・将来の保守者)、用途(判断を仰ぐ・報告・手順として実行・記録)、貼り先、トーンを確認する
- 分からなければ書き始める前に聞く。調査範囲・深さの質問と同時に聞く
- 読み手は会話を知らない前提で書く

## 骨子で合意してから本文を書く

- 本文の前に「冒頭の結論1行・見出し構成・各情報の置き場所」を示して合意を取る
- 「口語で」等の書きぶりの指示は、短いサンプルで確認してから全体に適用する

## 結論を先頭に置き、種類ごとの型に寄せる

- 報告: 結論(対応可能か) → 追加で必要なもの → 詳細
- レビュー: 判定(マージ可など)を1行目に → 「懸念 / 該当箇所 / 確認結果 / 対応不要ならその理由」の表
- 手順書: 重大な前提(止めてから実施する等)を強調 → 手順
- 残作業: 残っている作業だけ。完了したものは消す
- 技術レビュー資料: 非機能(コスト・性能・同時実行・ログ・監視)の章と、未着手タスクの先出し

## 情報の置き場所を3つに分ける

- 本文: 読み手の判断・行動を変えるもの
- 末尾の1節: 対象外・不採用(理由を1行ずつ)、問題なしだった詳細や実測値(「参考」として)
- 出さない: 確かめ切っていない「要確認」は確かめてから書く。ユーザーが判断できる論点は質問して片付け、資料に残さない
- チャットでの脇道の質問を資料に入れるかは都度確認する

## 会話や作業の痕跡を混ぜない

- AIとの会話の経緯(「当初〜と報告したが誤り」)、セッションの用語(「引継ぎ」「進捗」「ご相談したいこと」)を書かない
- 作業した主体(「AIが確認済み」)や決めた人の帰属を書かない。決定内容と正本の所在だけを書く
- 資料自体の位置づけ(commit対象か一時資料か)はチャットで伝え、本文に書かない
- 状況が変われば嘘になるステータスを書かない。満たすべき状態を書く

## 他者の領域に踏み込まない

- 相手が決めること(修正方針など)を提案しない。担当外の資料(他部署向けの早見表など)を作らない
- 他システムの不足を名指しせず、自分側の対処として書く

## 言葉を選ぶ

- 観点・見出しはユーザー自身の言葉(質問文)をそのまま使う。造語・内部の呼び名・抽象的な名詞句を使わない
- 注意書きは今回の対象に当てはまる事実だけ。対象外の条件の最悪ケースを断定で一般化しない
- 推奨には前提にしたパラメータと、根拠の種類(今の差か、将来の余裕か)を添える
- 異なる軸(ビジネス上の優先度と対応コスト等)を同じ並びで扱わない
- レビュー・指摘の資料では該当箇所と事実を示す。粗探しや頼まれていない観点は入れない
- 件数・曖昧語の扱いは concise-writing に従う

## 修正は差分で行う

- 指摘された箇所だけを直す。全文を書き直さない
- 「冗長」と言われたら量を減らす。直した後に行数が増えていないか確かめる
- 修正の報告は変えた点を数行で伝える

## 既存 skill との線引き

- 分量と取捨選択の基準は concise-writing、置き場所と表で一望する形は deliverable-presentation、判断ログは preserve-reasoning、手順のコマンドは reproducible-runbook
- この skill は、読み手の確定から差分修正までの手順と、資料内の情報の配置を扱う

## 禁止事項

- 読み手・用途・貼り先を確かめずに書き始めること
- 骨子の合意なしに長い本文を書くこと
- 結論が冒頭で読み取れない構成
- 対象外・不採用・問題なしの詳細に本文と同格の節を立てること
- 「要確認」やユーザーが判断できる論点を並べたまま提出すること
- 会話の経緯・作業ログ・決定者の帰属・資料の位置づけを本文に書くこと
- 相手が決めることへの提案や、担当外の資料の作成
- 造語・内部の呼び名・抽象的な名詞句
- 修正のたびに全文を書き直すこと、「冗長」の指摘に量を増やして応えること
