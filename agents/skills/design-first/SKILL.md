# Design First

いきなり実装しない。設計→合意→実装の順で進めるためのルール。

## 設計を先に提示する

- 非自明なタスクは、コードを書き始める前に設計・方針を提示して合意を得る
- 提示に含めるもの: 方針、影響範囲、複数案があり得る場合は比較と推奨案(+推奨理由)
- ユーザーは「まず設計をお願いします」を定型としている。依頼に明記がなくても非自明なら設計から入る
- 設計・方針を提案する前に、関連コードのコメント・docstring に書かれた設計判断を読む(「監視」「検知」など意図を表す語で横断して拾う)。提案では「コードが既に決めていること」と「今回決めること」を分ける
- 共通経路や全体のスキーマを変える手が混ざっていたら、避けて済む形を先に探す。触る既存ファイルの数を数え、保守コストとリスクが同等なら狭い案を推奨にする。広い案を採るなら、狭い形で足りない理由を書く
- plan を出す前に、確認できる事実は確認し切る。認証切れなどで確認できないものを「実装前の前提確認」として先送りせず、再認証を頼んで確かめる。確認の結果が選択肢を変えうるなら、確認の後に選択肢を出し直す
- 結論が「変更なし」になったら plan を作らず、本文で報告する。誤って作ったら削除して取り下げる

## 実装中の逸脱は立ち止まって報告

- 実装中に設計と食い違う事実が見つかったら、黙って軌道修正せず、いったん立ち止まって報告する
- ユーザーは推論の過程を監視して軌道修正したいと考えている。方針転換を事後報告にしない

## 承認ゲートを最後まで通す

- plan の要点はチャット本文にも出す。ファイルパス参照や承認ダイアログ任せにしない(ダイアログが消えると内容ごと失われる)
- 承認要求のターンに未決の確認事項を同梱しない。質問→回答→承認要求の順に分離する(同梱すると回答と承認が競合してプロンプトが潰れる)
- 承認を求めるときは「何の承認か・承認すると何が実行されるか(範囲・不可逆性)」を明示する。「このplanを承認してください」だけで何が起きるか分からない承認要求をしない
- 承認要求が中断(esc 等)されたら、ユーザーの次の入力に応対した後、自ら承認ゲートに戻る。「もう一度承認を求めてください」とタイプさせない

## 儀式化しない

- typo修正・自明な1行修正など、方針の分岐がない作業まで設計提示を要求しない。判断に迷ったら聞く

## 禁止事項

- 合意前の実装着手(非自明なタスクでいきなりコードを書くこと)
- 合意済み設計からの無断変更・無断拡張
- 設計に書いていない副作用(依存追加・設定変更など)を実装時に紛れ込ませること
- 中断された承認要求を放置し、ユーザーに再提示を依頼させること
- 承認の対象・範囲を示さない承認要求(ユーザーに「これは何の承認?」と聞かせること)
- 承認要求と未決の質問を同じターンに同梱すること
