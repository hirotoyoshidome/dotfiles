# Verify at Source

読めば確定できるものを「要確認」に残さない。推測や保守的な既定値ではなく一次情報で確定させる。

## 上流ソースを読む

- 調査を単一リポジトリに閉じない。依存先・上流のソースが参照可能なら読んで挙動を静的に確定する
- 「実機で叩かないと不明」と安易に決めつけない。ユーザーに「ソースからチェックすればいい」と言わせない
- 挙動だけでなく用語も上流に合わせる。上流を薄く包むものでは、利用者に見える表記を上流の画面の文言に合わせ、こちらの語感で言い換えない(利用者の言い方で引けないものは、存在しないのと同じになる)。表記を変えるなら件数を数えて多数派を採る

## 読む前にベースを最新にそろえる

- ローカルを読む調査の前に、対象リポジトリごとに現在のブランチ・追従先・最終 fetch・未コミットの変更を確かめ、fetch してベースブランチの最新にそろえる。未コミットの変更があるものは作業ツリーに触れず、`git worktree add --detach` で取り出して読む。plan モードを理由に先送りしない

## 手元に無いものは clone して読む

- ライブラリ・クライアント・SDK の対応状況は、Web 検索や公式ドキュメントで止めない。ドキュメントの「記載なし」は、非対応か未文書化かを判別できない。実装を読んで確定させる
- WebFetch・API・curl を1件ずつ叩いて承認を重ねない。調査の開始時に、対象(版を比べるなら現行版と最新版のタグ)をまとめて一時領域へ浅く clone し、以後はローカルで grep・diff する。1ファイルだけ・タグの有無だけでも clone を選ぶ。コード検索の API はヒット漏れがあり、網羅の根拠にならない
- clone したものはビルド・実行しない。調査が終わったら一時の clone は消す(チームのリポジトリは消さずに普段の作業場所へ移す)
- ソースが公開されていないものは、手元の実行ファイルに `strings` をかけて、宣言しているプロトコルの版や機能を確かめる
- 版上げの調査は、公式のアップグレードガイドを最初の一次情報として読む

## 前提は一次情報で確定する

- サポート範囲・バージョン・プラン制約・機能提供条件は公式の一次情報を確認して断定する。ユーザーに調べ直させない
- 確定できないものは「未確認」と明示し、何を確認すれば確定するかを添える

## 選択肢は標準機構の棚卸しから

- 解決策を出す前に、そのプロトコル・フレームワークが標準で持つ機構を洗い出す。ユーザーが他所から代替案を持ち込む状態は選択肢出しの不足

## 禁止事項

- 参照可能なソース・一次情報があるのに「要実機確認」「要検証」で止めること
- 推測やライブラリ既定値を確認済みの事実のように書くこと
- 案の成否を左右する前提を未確認のまま推奨を出すこと
- 上流のソースを clone せずに、Web 検索や API を1件ずつ叩いて承認を重ねること
